# 安装与回退

顺序是死的：**先让新的跑起来验通，再卸旧的**。反着一刀切，新插件哪个号没连上，那个号当场哑。

## 前置

- 每个 QQ 号的 OneBot 11 后端已经能收发（HTTP + WS 各一组端口）。
- 记下要接的会话 id（`session-…`）。当前会话可以在 DSH 的会话列表里看，带不带 `session-` 前缀本插件都认。
- 知道哪个 QQ 号算「主人」（写进 `owner`，投递时会标［主人］）。

## 零、装之前先看一眼清单

`package.json` 里的 `dsh.profile.bundles` 是**跟别的 agent 共用**的。装之前：

1. **在群里喊一声，等对方回「没在动」再动手。** 看修改时间只能说明刚才没动，说明不了下一秒——对方当场回一句比 mtime 靠得住。
2. 让对方面前查一遍 `bundles` 现在几项，自己也数一遍，两个数对上（本次是 29）。
3. 装完立刻再数一遍，应该是 30，而且多的是 `@local/dsh-qq-gateway`。

DSH 写这个文件有 `withFileLock` 和 `writeFileAtomic`，单次写不会写半截；但「各自读一遍再各写一遍」这个序列不原子，后写的照样盖前头的。所以别凭锁放心，靠错开时间。

## 一、装（不动旧的那套）

1. 在 **插件** 里用「添加插件」选中这个目录安装，或在有 `plugin_manager` 的会话里直接安装这个绝对路径。
2. 装完**重启 DSH**。插件跟宿主同进程，不重启等于没装。
3. 进设置里给 `qq-gateway` 填 `accounts`。先只填一个号，别一次填三个——出问题时要能一眼看出是哪个。
4. 重启，用 `qq_status` 确认：在线、登录号对得上、会话映射对得上、主人号对得上。

> 此时旧的 MCP 还在，所以这个会话里会出现两套 qq 工具。这是预期的，验完再卸。

> **验证期一定要给新插件填上 `label`**（比如填「新」）。两套同时挂着时，同一个号的消息会被投两遍、都落进同一个会话，看到重复时分不清是哪套通的。填了 label 之后，新插件投的每条唤醒头前面都会挂 `[新]`，一眼分得出。卸掉旧的那套后把这个标记清空。

## 二、一次重启把这八条走完

别来回重启折腾。装完这一次把下面八条一遍过（前七条验装通，第八条验真实节奏）：

1. **插件挂上了没** —— 插件列表里 `qq-gateway` 那一行是不是已启用。
2. **七个工具在不在** —— `qq_status`、`qq_send`、`qq_read`、`qq_mark_read`、`qq_profile`、`qq_lookup`、`qq_poke`。
3. **空账号时 `qq_status` 说什么** —— 应该是「还没有配任何 QQ 账号」，不是报错。
4. **填一个号之后收发通不通** —— 对面发一句能不能落进会话；会话回一句对面收不收得到。
5. **白名单外头真的不投** —— 找个不在名单里的号发一句，确认没动静、也没记账。
6. **点我名马上就投** —— 群里 @ 一下，应该走 1.2 秒那条快路，不是等攒批。
7. **重启后 state.json 还在不在** —— 再重启一次，看状态文件里那些会话记录还在（这是它跟纯内存实现的区别）。

8. **让群热闹一会儿，数日志不数感觉** —— 前面七条过了不算完。

   连着来十几条不点我名的，然后 @ 一下。**数日志里「投递」那几行**，别看会话里有没有消息——消息可能只是最后一轮带进来的。

   - 十几条闲聊 → 该是 **0** 行「投递」
   - 点你一次 → 才 **1** 行，而且那行的条数应该把前面十几条一起带进来
   - 要是热闹完冒出来五六行，说明攒批没生效，回去看 `batchQuietSec` 和 `groupWakeMode`

   每行长这样：`投递 hua group:100000001 批 30-45 共 16 条`

   **每条进来的消息都有一行去向，五个词**：

   | 词 | 意思 |
   |---|---|
   | `投递` | 真的推进会话了 |
   | `搁置` | 记了账但没投：群里没点名、没配会话、会话拿不到 agent |
   | `拦下` | 白名单外，当没来过 |
   | `丢弃` | 排队太久，过期丢了（只丢群聊，私聊和 @ 不丢） |
   | `失败` | 投出去了但没接住（超时或后端拒） |

   验的时候把五个词各自数一遍：进多少条，投递 + 搁置 + 拦下 + 丢弃 + 失败 加起来就该对上。

## 真机才露得出来的几样

单元测试是假的 ctx 加假的后端，管得住逻辑，管不住这些：

- **谁先到**：WS 连上那一刻，消息可能比 `probe` 先到。代码里已经用事件自带的 `self_id` 兜底，但没在真后端上跑过。
- **同一毫秒两条**：两个事件几乎同时到，合并槽必须只起一次投递。
- **乱序**：OneBot 的 seq 和到达顺序不一定一致。
- **断一下再连回来**：WebSocket 断开后重连，期间的消息是永久丢的（`docs/ROADMAP.md` 里记着补拉那条）。
- **引用和 @ 混着来**：一条消息里既 @ 我又引用我，两个都是「要紧」，看会不会重复算。

## 三、验通一个号

1. 让对方向这个号发一句，看有没有落进配置的会话。**看唤醒头有没有那个 `[标记]`**，没有的话就是旧的那套投的，不算新插件通了。
2. 从会话里用新工具回一句（`qq_send`，账号填新配的那个），看对方收不收得到。
3. 再验三条边界：
   - 群里没 @ 的闲聊能进来；
   - 群里 @ 一下能标出来；
   - 引用你那条回的能认出「引用了我那条」。

## 四、验通剩下两个号

每个号单独走一遍上面两步。三个号都通了再进下一步。

## 五、卸旧的两套 MCP

1. 卸/停用原来的 MCP 挂载（那两套 `snowluma` 与 `snowluma-her`）。
2. **重启 DSH**。
3. 再验一遍收发——这一步别省，卸旧的时候最容易把新的一起带下车。

## 六、回退

哪一步不对，立刻把旧的那套挂回去、重启，就能回到原状。本插件不动任何旧文件，也不改旧的配置，所以回退只是把旧挂载重新启用。

## 排错对照

| 现象 | 先看哪 |
|---|---|
| 收不到消息 | `qq_status` 里那个号是不是在线；`wsUrl` 有没有填；后端 WS 口开没开 |
| 消息进了错的会话 | `session` 填的是不是那个号的；`accounts` 里有没有两项填了同一个 `httpUrl` |
| 发不出去 | 后端 `accessToken` 对不对；单条是不是超过三千字 |
| 投进去但没人回 | `owner` 和 `allow` 配了没；白名单空数组是「谁都不理」 |
| 消息晚到或丢了 | 群里没点名的闲聊过五分钟会丢；私聊和 @ 不会丢 |
